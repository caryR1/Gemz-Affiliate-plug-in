**F10. Automated payout cron: what the empty `gas_last_automated_payout_run` does and does not prove (answer to Cary's question, 2026-09-19).**
Cary questioned my "almost certainly not configured" wording. He was right to: it overstated the evidence. Facts, from `GAS_REST::run_automated_payout()` and live reads:
- **When the option is written.** Only when an authenticated call gets past all gates: valid token, not paused, today's day-of-month is on or after `payout_run_day`, and this month has not already run. It is then written to the current month (`Y-m`), **even if nobody was eligible and even if no PayPal or Wise credentials exist** (the write is unconditional after the optional PayPal/Wise steps). A call that fails a gate writes nothing.
- **Which calls leave a trace.** Only the paused case writes an audit-log entry. A wrong token (403), "not yet run day" and "already ran this month" leave no record. So the audit log and the empty option cannot distinguish "cron never called" from "cron called too early or with a bad token."
- **Live values (read 2026-09-19 11:41 UTC):** site time is the 19th; `payout_run_day` 5; paused false; option empty; no payout-run audit entries. The token option exists, so the Ledger page (or an earlier call) had generated it before my tests.
- **Has a legitimate trigger date passed?** Yes, for the gate as coded. The feature exists in code since 2026-09-10, and on Solar the run is allowed on every day from the 5th of each month, including September. A daily cron pointed at this site with the right token would therefore have written `2026-09` on its first call from Sept 10 onward (nothing would have been paid: no closed-month balances, no credentials). Note the closed-month rule affects what gets **paid**, not whether the option is written.
- **Conclusion:** an empty option means no gate-passing call has reached this site's endpoint. That fits three situations equally: no cron; a cron with a wrong or old token (403) or aimed at another site; or a cron whose schedule has not yet reached a day on or after the 5th. It is **not** proof that the cron is missing. **Unverified**, not "almost certainly missing." Claude Code cannot read hPanel or the server crontab.
- **One real configuration trap to check:** a cron set to run **monthly on day 1 to 4** would call the endpoint on a day below `payout_run_day`, get `not_yet_run_day`, and **never run**, because the option is only written on a passing call. The schedule must be **daily**, or monthly on a day from the run day (5) through 28.
- **How Cary can verify without any code change:** in hPanel, Advanced, Cron Jobs, check that the job exists, its URL ends with the token shown at the bottom of the wp-admin Payout Ledger page, and its schedule is daily (or monthly on day 5 to 28). After the first call on or after the 5th, the Ledger page will say "last ran 2026-MM" instead of "has not run yet."
- **BUILT 2026-09-19 (v2.21.6, Cary: "sure its good to know") — cron call visibility, no payout behavior change.** `GAS_REST::run_automated_payout()` now records the time and outcome (`ran`, `already_ran_this_month`, `not_yet_run_day`, `paused`) of every authenticated call in the option `gas_last_automated_payout_call`, and remembers a wrong-token call (at most one write per hour, since that path is unauthenticated) in a one-hour transient. The Payout Ledger page shows "Last call from the cron: <time> — <outcome>" (or "none received yet"), a red note when a wrong or old token was used, and a sentence warning that a schedule that only runs before the run day never runs. Live test (in-process, no real run, no live setting changed): all four outcomes recorded correctly, the 403 case set the marker, the page rendered. One test side effect was an empty `gas_last_automated_payout_run` option; it was deleted, and the option is absent again exactly as before.

**F11. Tax and payment data encrypted at rest (v2.22.0, live 2026-09-19, Cary: "lets do tax-data encryption").**
- **What is encrypted:** tax ID (SSN/EIN), tax legal name and country; PayPal email, Wise account name, account number/IBAN and routing number, payment notes; and the buyer cash-back payment details stored on payout rows. Left plain on purpose: payout method, currency, transfer type, tax form type and the tax-submitted timestamp (not sensitive, and other code reads them directly).
- **How:** new `class-gas-crypto.php`. AES-256-GCM (OpenSSL, authenticated), random IV per value, stored as `gasenc1:` + base64. Each value is bound to its owner and field (authenticated data such as `u42:gas_tax_id`), so ciphertext copied to another user or field will not decrypt; tampering is detected. All reads and writes already funneled through `GAS_Payouts::get_details/save_details/get_tax_info/save_tax_info` and the cash-back pair, which now encrypt and decrypt. OpenSSL was chosen over libsodium because the server's PHP has no sodium extension.
- **Key:** `GAS_DATA_KEY` (base64 of 32 random bytes) in the site's `wp-config.php`, outside the database. `wp-config.php` was backed up before the edit (in the hosting account's home folder, outside the web root) and tightened to owner-only permissions (600). A copy of the key is in the local, git-ignored `.secrets/solar-gas-data-key.txt`. **The key must also be backed up in a password manager: if it is lost, encrypted values are unrecoverable and affiliates would have to re-enter them.**
- **Behavior without a valid key:** writes fall back to plaintext and the Payout Ledger page shows a red "Encryption is NOT active" notice (a shared plugin must not break another site that has no key yet). Reads of an encrypted value with a missing or wrong key return empty (never ciphertext or a crash), and the tax export marks the tax ID `UNREADABLE (encryption key missing or changed)`. Legacy plaintext still reads normally, and `GAS_Crypto::migrate_plaintext()` (idempotent; verifies each value decrypts back before writing) converts old rows. The Ledger page shows how many plaintext values remain.
- **What it protects:** database dumps, hosting backups of the database, SQL-injection reads and other plugins reading user meta now see only ciphertext. **What it does not protect:** anyone who can read `wp-config.php` or run PHP on the server, or an admin with server access (the key must be readable by the site).
- **Solar's data at rollout:** zero tax or payment values existed, so nothing needed converting; the migration was exercised on a test record.
- **Live tests, all passed, all test data removed:** every field stored encrypted with no plaintext anywhere in usermeta; read-back through the real methods; masked summaries unchanged; ciphertext copied to another user unreadable; legacy plaintext read then migrated (second run a no-op); wrong key gives empty values, an `unreadable` flag and no crash; the PayPal and Wise eligibility functions run against encrypted data; the accountant tax export shows the decrypted tax ID; cash-back details encrypted and masked summary intact; the Ledger page shows the status line. PHPUnit now 47 tests / 107 assertions (10 new in `CryptoTest.php`).
- **Not covered / follow-ups:** the PayPal client secret and Wise API token still sit in `wp_options` in plaintext (they could move to wp-config constants); signup IP and phone numbers are not encrypted; any other site running this plugin (for example Home) needs its own `GAS_DATA_KEY` and a run of `GAS_Crypto::migrate_plaintext()` after it deploys v2.22.0; no key-rotation tool (the `gasenc1` prefix leaves room to add one).
